
3. SEAL v0.2 — NEW DOMAIN vs SAME-DOMAIN-APPEND
----------------------------------------------------------------------

**New domain is correct.** Do not same-domain-append.

  v0 domain (SEALED behavior):  QORTROLLER-POEP-GAMEPLAY-LIVESEAL-v0-CANDIDATE
  v0.2 domain (NEW):            QORTROLLER-POEP-GAMEPLAY-LIVESEAL-v0.2-CANDIDATE

Why not append on the same domain string:
  - Verifiers that only know v0 will mis-handle longer preimages or silently
    accept wrong length if they slice/stop early.
  - Cross-version confusion: same tag, different field count = audit nightmare.
  - Repo convention for candidate tags is version-in-tag (v0 / v0.2), not silent
    preimage growth.

**Binding subtlety — CRITICAL FIX before build (claim vs preimage mismatch):**

Claude / open doc claim:
  "v0.2 distinguishes NFT/TBA-custody epochs… If the controller NFT were ever
   transferred out of the TBA / the DID reissued, pre- and post-custody seals
   are cryptographically distinguishable."

Proposed preimage append: only `|controller_nft_token_id`.

**That claim is false under that preimage.** ERC-721 tokenId is stable across
transfer. tokenId 1 remains 1 whether TBA holds it or a stranger does. Binding
only token_id distinguishes *which NFT instance*, not *who holds it*.

Honest options (pick before code; do not ship the false epoch claim):

  (H1) **Honest narrow claim (minimal preimage):**
       Append only controller_nft_token_id (and optionally contract address).
       Document epoch as: **NFT-instance epoch** (different tokenId → different
       seal). Explicitly: **does NOT** detect TBA transfer / custody change.
       Rename mental model away from "custody epoch" in every string/test doc.

  (H2) **True custody-epoch claim (recommended if you want the open-doc prose):**
       Preimage append must include a custody locator that *changes* on transfer,
       e.g. `|controller_nft|token_id|tba_address` (or `|owner_did`).
       Then the open-doc custody-epoch sentence is true.
       Still NEW domain v0.2. Still candidate.

  (H3) **Do not bind registration_tx into the live seal** as a stand-in for
       custody — that is ceremony provenance (one-time), not ongoing custody.

Also pin:
  - `compute_live_seal(...)` v0 stays byte-identical (golden vectors in
    test_poep_gameplay_live.py must not move).
  - Prefer `compute_live_seal_v02(...)` (or kwargs only on a *new* function) —
    never add optional trailing args to v0 that change default domain.
  - `verify_live_seal` stays v0-only unless a separate `verify_live_seal_v02`
    is added; do not dual-accept under one function without an explicit
    `seal_version` argument (version-confusion risk).

Process nonce + session_id + device_id + t_start_ns remain; v0.2 only *adds*
custody/instance fields after a new domain tag.

4. FIELD NAMES THAT STILL ENABLE OVERCLAIM
----------------------------------------------------------------------

Even with correct values, these names greases wrong narratives:

| Name / shape                         | Risk                                      | Safer shape |
|--------------------------------------|-------------------------------------------|-------------|
| `device_identity_chain`               | "device DID" collapse                     | `device_to_owner_link` / `device_custody_chain` |
| flat `owner_did` on presence schema  | "this presence session is DID-certified"  | nest under `identity` + new schema |
| `identity_advisory` alone            | soft; without advances_* looks optional  | + `advances_poep_enabled: false` + `advances_presence_session_candidate: false` (mirror controller_presence) |
| `ioid_token_id` at top level         | "ioID authenticated this play session"    | nest; comment: ceremony id, not session auth |
| `registration_tx` without role       | "tx proves presence"                      | keep; pair with claim_ceiling; role = ioID register only |
| `controller_nft` naming              | fine if inside link object                | do not call it `device_did_nft` |
| any key `*sovereign*`                | bar-1 magnet                              | ban in denylist |
| `lane: "identity-provenance"`        | good                                      | keep exact string; test equality |
| reusing summary key `claim`          | presence claim string is liveness-shaped  | use `claim_ceiling` only for identity attach; do not overwrite summary["claim"] |

**Non-claim machine fields (strongly recommend, already proven pattern):**
  advances_poep_enabled: false
  advances_presence_session_candidate: false
  identity_advisory: true          # or advisory: true inside identity block
  identity_lane: "identity-provenance"
  did_subject: "gamer_wallet"
  did_names_silicon: false

Do **not** add:
  device_did, sovereign_did, edge_did, presence_did, authenticated_did,
  identity_verified_session, did_bound_presence, custody_proves_human, etc.

Constants from r01 table are fine as test fixtures / optional defaults behind
an explicit "live ceremony constants" helper — but the wrapper should take them
as **arguments**, not hard-bind the single Edge as the only legal device without
a guard. Guard already requires summary.device_id == chain.device_id — keep that;
do not silently overwrite summary.device_id with the ceremony Edge.

Normalize comparison: hex case / 0x prefix. Fail closed on mismatch (ValueError),
never "soft warn and attach."
