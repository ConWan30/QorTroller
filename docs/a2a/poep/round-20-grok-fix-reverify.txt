### 1. Continuous-poll vs residual cadence tell

**Trace (`_fire_probe_silent`):**

```
while mono < fire_at:  poll → ring.append → sleep(poll_interval)   # ~8ms
pre = list(ring)
poll  # r2_at_probe
profile = l6b_probe_profile(...)
probe_ts / t_challenge_ns          # stamped BEFORE write
_sync_write(force)
while mono < deadline: poll → [maybe asyncio.run(clear_triggers)] → sleep(8ms)
```

**Does it close the silence→burst pre-tell?** Yes. From `t_arm` there is no quiet→dense transition ~200–600 ms before force. A pure INPUT-poll-rate watcher sees ~125 Hz from arm; the CSPRNG delay is not keyed by a burst edge.

**Is pre→post cadence uniform?** No. At the fire boundary:

| segment | inter-poll spacing |
|---|---|
| pre loop | ≈ `poll + 8ms sleep` |
| last pre → r2 poll | ≈ 8ms (full sleep after last ring sample, then exit) |
| r2 poll → first post poll | **profile + `_sync_write` only — no `sleep`** → often **&lt;8ms** (compressed) |
| mid-post at `hold_ms` | `asyncio.run(clear_triggers)` inserts a **blocking stall** |

Those discontinuities sit **at/after** `t_challenge` / force write (and later at clear). That is **A-REACTIVE-adjacent** (onset-coupled), not a **pre-fire** tell.

**“One iteration early”?** Not as a pre-tell. Last ring sample is always under `mono < fire_at`; then a full 8ms sleep; then exit; then r2 poll + stamp + write. Worst lag after intended `fire_at` is ~one poll period + write cost (well inside `SCHEDULE_TOLERANCE_MS=300`). There is no observable “about to fire in ~pre_count×8ms” edge before the force. The r2 poll is still a normal INPUT read, ms before write — not a 200–600ms arm cue.

**Verdict on (1):** Burst residual closed. Remaining cadence wiggle is at fire / clear, out of P-LIVE-0 claim.

### 2. Harness honesty (continuous → 0.02)

Modeling `poll_burst_watcher` on `continuous_poll` as **blind uniform-delay + 150ms** is the **right** model for a bot whose only signal was the burst edge.

Could continuous-poll-aware timing beat blind?

| signal | leak? |
|---|---|
| `t_arm` = when continuous poll starts | Yes, but blind already conditions on `t_arm` |
| ring fill / first `pre_count` polls | No — fill finishes in ~0.2–0.6s; fire is still U[3,12]s |
| `fire_at = t_arm+delay` | Only if delay known; delay is independent CSPRNG, not printed pre-fire |
| multi-trial learning | Independent draws; single-shot FAR floor unchanged |
| short inter-poll at fire / OUTPUT force | A-REACTIVE, explicitly out of harness |

**0.0225 is not flattering** under a non-reactive timing adversary: acceptance width ~220ms over ~9s span → ~0.024. That is the information-theoretic floor for this delay window + reaction band. Harness is honest for its threat model; it does **not** prove “no HID-output bot.”

### 3. Is `O_opt = mid(est_pre)+190` strongest?

On `sleep_then_burst` with **unknown** `est_pre ~ U[208,600]`:

- Accept when `est_pre ∈ [O−300, O−80]` (220ms window).
- Any fixed `O ∈ [508, 680]` saturates at **220/392 ≈ 0.56**.
- `mid+190 = 594` is in that plateau (measured 0.5575). Scanning fixed offsets does **not** beat ~0.56.

**Stronger if `est_pre` known exactly** (fixed public `pre_count`, count down): fire `t_burst+est_pre+150` → **FAR → 1.0**. That needs a known remaining pre-window, which continuous poll removes (no burst start). Randomized `pre_count` is what keeps the naive path at ~0.56 rather than 1.0.

**Fix still passes** if you strengthen the naive bot (naive FAR only rises; `fixed ≤ 0.15` unchanged). Flaw is not under-shown in a way that flatters the fix.
