## A — Device-ts latency: right fix? Same clock?

**VERDICT: YES — device-ts is the right fix; probe and crossing MUST share the device clock (last pre-frame device_ts at fire, not monotonic).**

**Why:** `send_l6b_probe` returns `time.monotonic()`; crossing uses `t_mono` stamped when the session loop builds `_l6b_entry` — both are bridge receive time, so RP burst lag inflates both ends of a mismatched pair. Device 3 MHz uint32 (offset 28) is already proven on the l2_ads path; the analyzer never sees it.

**Same-clock rule (non-negotiable):**

| Instant | Source | Not this |
|--------|--------|----------|
| `probe_device_ts` | last `_l6b_pre_buffer` entry with valid `device_ts` **at arm/fire** (snapshot before write is fine) | `time.monotonic()` from `send_l6b_probe` |
| `crossing_device_ts` | first post frame above threshold with valid `device_ts` | `t_mono` on that frame |

```text
device_latency_ms = wrap_u32(crossing_device_ts - probe_device_ts) / 3000.0
# 3 MHz → ms; wrap every ~1432 s
```

**Bias:** last-pre is ≤1 poll sample early (~8 ms at `dt_ms=8`) — inside band noise, not the 3–15× RP error.  
**Gap:** `InputSnapshot` / `_poll_frames` do **not** surface offset 28 today (IMU uses `states[16:28]` only). Build must extract `states[28:32]` (USB dual-connect path) into the snap → `_l6b_entry`. Do not mix hid-counter ts with pydualsense frames without a join key.
