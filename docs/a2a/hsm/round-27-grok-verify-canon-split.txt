## Findings (severity order)

### F1 — MEDIUM — Library trust boundary: caller-supplied `on_chain_pubkey_hash_hex` is circular-forgeable

`verify_registered_device_binding` trusts whatever hex the **caller** passes. Empirically:

```text
verify_registered_device_binding(arbitrary_id, attacker_key,
    on_chain_pubkey_hash_hex=compute_pubkey_hash_hex(attacker_key))
→ True
```

That is not “chain wins”; it is “hash-of-local-key wins.” The natural footgun is worse than pre-split skip-verify because it **looks** like the secure path:

```python
verify_cert(cert, on_chain_pubkey_hash_hex=compute_pubkey_hash_hex(cert.ecdsa_p256_pubkey_hex))
```

grandfathers **any** `device_id` for a correctly signed cert without RPC.

**Mitigations already present (correct):**
- `scripts/verify_device_cert.py` fetches `devices(id).pubkeyHash` from VMDR after `registered==True`
- `--reissue` same: RPC-only, no offline fallback
- Malformed hash / empty string fail-closed (length ≠ 64)
- Offline/`None` never skips (T-BIND-4, live offline fail)

**Gap:** docstring describes “caller read … from VMDR” but does **not** hard-warn: *never pass `sha256(local_pubkey)`; evidence must be RPC-fetched for that `device_id`*. Compare pre-split: careless caller could omit the check; post-split, careless caller can pass a self-hash and believe they verified. Same root of trust class (caller honesty), **subtler UX hazard**.

**Not a Path A exploit** if only the shipping scripts call the library. Still a real API footgun.
