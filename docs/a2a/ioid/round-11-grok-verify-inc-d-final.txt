### DELTA 1 — dev-self `BRIDGE_PRIVATE_KEY` fallback

**Could this sign with the bridge key for a non-bridge gamer?**  
**No.** Two independent stops:

1. **CLI gate (necessary condition):** fallback only when `not key` **and** `args.gamer.lower() == 0x0Cf36dB5…`. Non-bridge `--gamer` never loads `BRIDGE_PRIVATE_KEY`.
2. **Core gate (sufficient condition):** `Account.from_key(gamer_private_key).address` must equal `gamer` or register raises. Wrong key × wrong gamer cannot broadcast.

**Key priority (safe):** `--gamer-key` → `GAMER_PRIVATE_KEY` → (dev-self only) `BRIDGE_PRIVATE_KEY`. Explicit keys always win.

**Key leak?**  
**No.** Prints only the honest note (env *name*, not material). Result JSON has device/tba/tx — never the key. Key stays in env/process memory (same as existing bridge ops).

| Adversarial case | Result |
|---|---|
| `--gamer` ≠ bridge, no key | fallback OFF → exit 2 on `--confirm` |
| `--gamer` ≠ bridge, bridge key forced via env as `GAMER_PRIVATE_KEY` | core address mismatch → refuse |
| `--gamer` = bridge, no explicit key | fallback ON — intended |
| whitespace / mangled gamer | no match → fail-closed |
